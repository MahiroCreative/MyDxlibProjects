## 3. 自動検証

```
cd extension
npm install
node esbuild.js && npx tsc --noEmit -p ./
node test/runTest.js <作業フォルダ> "<SDK フォルダの絶対パス>"
```

- 作業フォルダは空きの一時フォルダ(検証用の VSCode プロファイル・拡張・スクリーンショットがここにできる)。
- 段階 1〜5 が順に走る。所要は約 6〜8 分(段階 1 に 125 秒の待機がある)。
- 出力の `[phaseN] OK/NG` を数える。集計行は「失敗 0 件」と出る。
- スクリーンショットは `<作業フォルダ>/screenshots/`。合否ではなく、人(Claude)が画像を見て判断する。

**踏みやすい落とし穴**

- Claude Code など VSCode の拡張の中から実行すると `ELECTRON_RUN_AS_NODE=1` が引き継がれ、Code.exe が Node として動いて失敗する。`runTest.js` が消している。
- VSCode 本体が自動更新中だと、検証用の VSCode も「Code is currently being updated」で起動できない。更新プログラム(`CodeSetup-*.exe`)が、今使っている VSCode の終了待ちで止まることがある。**ユーザーの VSCode を勝手に閉じない**。ユーザーに再起動してもらう。
- 実機で動かす検証は、確認ダイアログを `showErrorMessage` などの差し替えで自動応答させている。差し替えは必ず `finally` で戻す。
- C/C++ 拡張の「定義を作成」は、編集を未保存のまま残す。検証はディスクではなく開いているドキュメントを見る。片づけは「保存 → エディタを閉じる → パターン一致で削除」。
- VSCode はパスのドライブ文字を小文字(`c:\`)で返す。設定値の比較は大文字小文字を無視する。

## 8. 決定事項の要約(詳細は DESIGN.md)

- 対象は生徒。UI はすべて日本語。コマンドパレットは使わせず、パネルのボタンとフォームで操作する。
- 配布は VSIX の直接インストール(Marketplace には出さない)。**VSIX はダブルクリックさせず `install.bat` を使う**(18 章)。
- SDK は生徒が自分で置きパスを指定する。ダウンロード機能は作らない。間違いでも保存して ✗。正しくない間はプロジェクトを作成できない(5 章)。
- ビルドは `cl.exe` 直叩き(CMake は必要になったら検討)。ソースは BOM 付き UTF-8 + `/source-charset:.932 /execution-charset:.932`(`/source-charset:utf-8` は DxLib.h の日本語コメントが警告の洪水になるので不可)。
- テンプレートは「フォルダ 1 つ = 1 テンプレート」(`template.json`)。同梱は「最小」のみ。`__PROJECT_NAME__` を置換。
- シェーダーは Direct3D 11 モードで教える。既定ターゲットは `vs_4_0` / `ps_4_0`(DxLib 本体と同じ)。
- ライセンスは MIT(`extension/LICENSE`)。`00_DxLib_Make`(DxLib のソースパッケージ)は DxLib 作者のライセンスで、MIT の対象外。リポジトリには入れる。
- ウォークスルーの画像は付けない。
- Direct3D 9 と 11 の違いの経緯(2D と 3D で入力の並びが違う理由): D3D9 版の 2D 描画は頂点シェーダーを使わず、D3D9 のピクセルシェーダーは入力を名前で受け取っていたので順番は無関係だった。D3D10 以降は順番で結び付く。DxLib は D3D9 時代の使い方のまま D3D11 対応したので、「2D では自作の頂点シェーダーが無視される」「入力の並びを合わせないと壊れる(エラーも出ない)」が生まれた。ユーザーは仕様として受け入れた。
